# Implementation decisions

1. **Hosted showcase adapter.** The production/academic target remains Docker Compose, PostgreSQL, NestJS, Vite, and Socket.IO. Because the private Sites runtime does not support raw PostgreSQL TCP connections, the deployed showcase uses its bound D1 database for persisted tickets, sequences, events, fairness state, and live polling. It implements the principal queue workflow for an owner-only preview, while the PostgreSQL/NestJS applications remain the deployment target and source of the full security/concurrency model. Existing D1 table names containing `qms_demo_` are retained only because renaming applied hosted migrations would risk data loss; they are not user-visible or canonical entities.
2. **Ticket lookup proof.** A six-digit code is Argon2id-hashed. A signed 24-hour lookup token supports QR use. The one-time code is returned only on initial creation. Idempotent replays return the same ticket and signed token, not the plaintext code.
3. **Business date.** The branch-local date is computed using the IANA timezone, represented as a PostgreSQL `DATE`, while operational timestamps use `TIMESTAMPTZ`/UTC.
4. **Fairness scope.** Consecutive priority calls are derived from recent call events for the branch/service. This keeps fairness consistent when multiple counters serve one service.
5. **Refresh sessions.** Refresh tokens are held in strict HTTP-only cookies; only SHA-256 token fingerprints are stored. Rotation revokes the previous record.
6. **No Redis in MVP.** A single API process owns Socket.IO fan-out. Redis remains a future horizontal-scaling option.
7. **Customer identity boundary.** The canonical customer app supports account registration and stores only name, normalized email, credential hash, lockout state, and ticket ownership. It does not collect banking credentials. The hosted showcase additionally gives each private showcase identity an isolated synthetic, read-only portfolio so the broader product journey can be demonstrated without connecting a core-banking system. The kiosk remains anonymous and uses private lookup proof. Priority reason is private and omitted from public events.
8. **Report truth.** Reports query tickets, events, and sessions directly. CSV export calls the same report service used by the dashboard.
9. **Development device secrets.** Kiosk and display builds require explicit environment-injected provisioning values. No working device secret is present in source. Production must inject per-device secrets through controlled provisioning and must not compile reusable shared production secrets into public bundles.
10. **WorldLink showcase identity.** At the owner's direction, the user-facing academic showcase is branded `WorldLink Bank`, uses the supplied emblem, and exposes Summit, CMC, Ayat, Piyassa, 4 Killo, Stadium, Megenagna, Mexico, Bole, Shola, and Lideta. Visible notices identify account balances and activity as synthetic demonstration data and make clear that the showcase cannot perform real banking transactions.
11. **Dedicated hosted surfaces.** The hosted showcase uses `/kiosk`, `/display`, `/staff/login`, `/teller`, and `/manager` rather than a role-switching tab shell. HTTP-only sessions and mutually exclusive server-side role checks keep Manager and Teller workspaces separate in both directions. Changing staff identity requires an explicit logout. The Site itself remains owner-only for controlled academic demonstration.
12. **Hosted credential adaptation.** Showcase staff passwords are verified with WebCrypto PBKDF2-SHA-256 using per-account salts and 100,000 iterations, the maximum accepted by the Cloudflare Workers runtime; only derived hashes are committed. The PostgreSQL/NestJS target uses Argon2id. Hosted sessions use random opaque tokens, store only SHA-256 token hashes, expire after four hours, and support revocation.
13. **Native Android applications.** Customer and teller use separate Android application IDs and native Jetpack Compose interfaces sharing a `mobile-core` Android library. The library provides encrypted Keystore token storage, refresh rotation, REST and Socket.IO connectivity; all business rules still remain in the NestJS workflow services. Administrator and manager workspaces and the public display stay on the web because they are operational large-screen surfaces.
14. **Mobile refresh transport.** Browsers continue to receive refresh tokens only through HTTP-only strict cookies. An Android client identified by `X-Client-Platform: android` receives the rotating refresh token in the TLS-protected response body and submits it through `X-Refresh-Token`; the app encrypts it at rest with an Android Keystore AES-GCM key. Release builds require HTTPS.
15. **Optional kiosk.** The customer mobile app is the primary personal ticket channel. The web kiosk remains a branch-owned fallback for accessibility, device, connectivity, and battery constraints; it is not required for a customer who can use the mobile app.
16. **Signing boundary.** Repository automation builds debug APKs for private demonstration. Production signing material is never generated or committed automatically; Play Store/AAB release signing must use an owner-controlled keystore or Play App Signing.
17. **Customer email verification.** Email ownership verification and password recovery require an external mail provider and are deferred. Registration is immediately active in this academic MVP; production rollout must add verified email and recovery before accepting real customers.
18. **Idempotent issuance lock.** Ticket issuance takes a PostgreSQL transaction-scoped advisory lock derived from branch, actor, operation, and idempotency key. Ticket creation, event writes, daily sequence allocation, and the idempotency record commit atomically, so simultaneous retries cannot create duplicates.
19. **Idempotent teller mutations.** Call Next, Recall, Start Service, Complete, No-Show, and Transfer require UUID request keys. Each state change, immutable event, and replay record commits together; a replay returns the original ticket without sending a second real-time announcement.
20. **Owner-authenticated showcase access.** The owner-only hosted compatibility preview can create a Manager or Teller showcase session from the hosting platform's authenticated-user header, so no working preview password is stored in source. This shortcut is absent from the canonical NestJS API and must not replace staff authentication in a public deployment.
21. **Shared service queues.** Customer tickets remain in the selected service queue and are not pre-assigned to a teller. An eligible teller calls the next ticket from the service assigned to that teller's counter. This avoids stranded tickets when a teller pauses or signs out and matches the approved bank workflow.
22. **Manager-controlled teller counters.** A teller account has at most one assigned counter, and one counter has at most one assigned teller in the MVP. Only a manager may create or change this assignment. The teller UI exposes only the assigned counter, and the API rejects a forged request to open another counter.
23. **Concurrent fairness serialization.** PostgreSQL Call Next keeps `FOR UPDATE SKIP LOCKED` ticket selection and adds a branch/service advisory transaction lock around the priority-lane decision. This preserves the exact configured priority streak even when multiple eligible counters call simultaneously. The hosted D1 adapter keeps an independent fairness streak per service.
24. **Remote reservation eligibility.** A home booking starts in `RESERVED` and is excluded from Call Next until the customer confirms physical arrival using a short-lived branch code. On-time check-in changes it to `WAITING` without replacing `queue_entered_at`, preserving the customer's original booking order. Expired reservations are terminal and do not block checked-in customers.
25. **Remote abuse controls.** The hosted customer portal permits one active remote ticket per customer per branch, three issuances per business day, a ten-minute cooldown after cancellation, idempotent retry, and a temporary restriction after repeated expiry/no-show incidents. The owner-private platform identity is hashed for the showcase; a pilot must replace it with verified phone OTP and an abuse-risk service.
26. **Priority verification.** A customer may privately request elderly, disability, pregnancy, accessibility, or exceptional priority assistance, but remote self-selection does not activate priority. Teller/manager verification is audited, public payloads omit the reason, and the starvation-safe configured consecutive-priority limit remains authoritative.
27. **Read-only banking overview.** The customer showcase persists two synthetic, identity-owned accounts and a small transaction history in D1. Account numbers are masked, lookups are bound to the authenticated showcase subject, and statement exports repeat the demonstration warning. There are deliberately no transfer, payment, beneficiary, card-control, or balance-mutation endpoints. A real deployment must integrate an approved core-banking API behind a separate, strongly authenticated domain boundary.
28. **Independent staff actors.** Administrator, manager, and teller are mutually exclusive authenticated roles with one workspace each and a visible logout action. `/admin` owns branch, user, counter, service, configuration, security, and audit controls under API-enforced `ADMIN` guards. `/manager` owns live branch operations and reports under `MANAGER`; `/teller` owns only the assigned counter under `TELLER`. A current browser session must be logged out before a different staff identity can sign in, and no workspace contains actor-switch links.
