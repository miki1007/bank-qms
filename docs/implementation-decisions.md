# Implementation decisions

1. **Hosted showcase adapter.** The production/academic target remains Docker Compose, PostgreSQL, NestJS, Vite, and Socket.IO. Because the private Sites runtime does not support raw PostgreSQL TCP connections, the deployed showcase uses its bound D1 database for persisted tickets, sequences, events, fairness state, and live polling. It implements the principal queue workflow for an owner-only preview, while the PostgreSQL/NestJS applications remain the deployment target and source of the full security/concurrency model. Existing D1 table names containing `qms_demo_` are retained only because renaming applied hosted migrations would risk data loss; they are not user-visible or canonical entities.
2. **Ticket lookup proof.** A six-digit code is Argon2id-hashed. A signed 24-hour lookup token supports QR use. The one-time code is returned only on initial creation. Idempotent replays return the same ticket and signed token, not the plaintext code.
3. **Business date.** The branch-local date is computed using the IANA timezone, represented as a PostgreSQL `DATE`, while operational timestamps use `TIMESTAMPTZ`/UTC.
4. **Fairness scope.** Consecutive priority calls are derived from recent call events for the branch/service. This keeps fairness consistent when multiple counters serve one service.
5. **Refresh sessions.** Refresh tokens are held in strict HTTP-only cookies; only SHA-256 token fingerprints are stored. Rotation revokes the previous record.
6. **No Redis in MVP.** A single API process owns Socket.IO fan-out. Redis remains a future horizontal-scaling option.
7. **Customer identity boundary.** The customer app supports account registration and stores only name, normalized email, credential hash, lockout state, and ticket ownership. It does not collect banking credentials or transaction data. The kiosk remains anonymous and uses private lookup proof. Priority reason is private and omitted from public events.
8. **Report truth.** Reports query tickets, events, and sessions directly. CSV export calls the same report service used by the dashboard.
9. **Development device secrets.** Kiosk and display builds require explicit environment-injected provisioning values. No working device secret is present in source. Production must inject per-device secrets through controlled provisioning and must not compile reusable shared production secrets into public bundles.
10. **Neutral product identity.** The application is a portfolio/academic product rather than a commissioned system for a real bank. User-facing branding uses `Bank QMS`; the development branch uses the neutral identity `Main Branch` and `MAIN`.
11. **Dedicated hosted surfaces.** The hosted showcase uses `/kiosk`, `/display`, `/staff/login`, `/teller`, and `/manager` rather than a role-switching tab shell. HTTP-only sessions and server-side role checks prevent Teller access to Manager data and mutations. The Site itself remains owner-only for controlled academic demonstration.
12. **Hosted credential adaptation.** Showcase staff passwords are verified with WebCrypto PBKDF2-SHA-256 using per-account salts and 100,000 iterations, the maximum accepted by the Cloudflare Workers runtime; only derived hashes are committed. The PostgreSQL/NestJS target uses Argon2id. Hosted sessions use random opaque tokens, store only SHA-256 token hashes, expire after four hours, and support revocation.
13. **Mobile packaging.** Customer and staff use separate Android application IDs and separate iOS bundle IDs but intentionally reuse their connected React experiences through hardened native web shells. This avoids duplicating business rules, keeps HTTP-only sessions and the backend authoritative, and permits eventual native-screen migration without changing API contracts.
14. **Optional kiosk.** The customer mobile app is the primary personal ticket channel. The web kiosk remains a branch-owned fallback for accessibility, device, connectivity, and battery constraints; it is not required for a customer who can use the mobile app.
15. **Signing boundary.** Repository automation builds debug APKs for private demonstration. Production signing material is never generated or committed automatically; Play Store/AAB release signing must use an owner-controlled keystore or Play App Signing.
16. **Customer email verification.** Email ownership verification and password recovery require an external mail provider and are deferred. Registration is immediately active in this academic MVP; production rollout must add verified email and recovery before accepting real customers.
17. **Idempotent issuance lock.** Ticket issuance takes a PostgreSQL transaction-scoped advisory lock derived from branch, actor, operation, and idempotency key. Ticket creation, event writes, daily sequence allocation, and the idempotency record commit atomically, so simultaneous retries cannot create duplicates.
18. **Idempotent teller mutations.** Call Next, Recall, Start Service, Complete, No-Show, and Transfer require UUID request keys. Each state change, immutable event, and replay record commits together; a replay returns the original ticket without sending a second real-time announcement.
19. **Owner-authenticated showcase access.** The owner-only hosted compatibility preview can create a Manager or Teller showcase session from the hosting platform's authenticated-user header, so no working preview password is stored in source. This shortcut is absent from the canonical NestJS API and must not replace staff authentication in a public deployment.
20. **Shared service queues.** Customer tickets remain in the selected service queue and are not pre-assigned to a teller. An eligible teller calls the next ticket from the service assigned to that teller's counter. This avoids stranded tickets when a teller pauses or signs out and matches the approved bank workflow.
21. **Manager-controlled teller counters.** A teller account has at most one assigned counter, and one counter has at most one assigned teller in the MVP. Only a manager may create or change this assignment. The teller UI exposes only the assigned counter, and the API rejects a forged request to open another counter.
22. **Concurrent fairness serialization.** PostgreSQL Call Next keeps `FOR UPDATE SKIP LOCKED` ticket selection and adds a branch/service advisory transaction lock around the priority-lane decision. This preserves the exact configured priority streak even when multiple eligible counters call simultaneously. The hosted D1 adapter keeps an independent fairness streak per service.
